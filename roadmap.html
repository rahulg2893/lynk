Decisions made along the way

  • Personal chat, not a workplace tool (v3 to v4).
  • Removed the prompt.txt effects and Lenis smooth scrolling in favour of a few purposeful animations.
  • Moved from pink and plum to Apple greys with a blue accent.
  • Account screens run on a mock store shaped like the future API (src/lib/account.ts), so wiring the server changes data calls, not pages.
  • The theme switch moved from the app dock into Settings › Appearance, with Match system as the default.
  • One repo for every app: apps/web now, then apps/ios and apps/android, plus apps/server for the Go backend.
  • Open decision: the plan so far is one Expo app for both phones, but the repo now expects separate ios and android folders. Decide before phase 3: one Expo app (shared code, generated protocol, one team) or two native apps (SwiftUI and Kotlin, roughly double the mobile work).
  • A red token for destructive actions only: --danger #D70015 (white text 5.38:1) and --danger-ink #FF6961 in dark (6.03:1).
  • "Nearby mode" (chatting with no internet over Bluetooth and Wi-Fi) is possible in the mobile app but deferred until after v1.

Next up: the backend half of phase 0. Add apps/server with the Go skeleton and Docker Compose, then connect the existing sign-in screens to real passkeys, Apple and Google.

Conflicts and how they are resolved

A personal app raises different trade-offs than a workplace one. These five decide the shape of v1.

1. Smart features vs end-to-end encryption

People expectPersonal chats to be private, and many expect end-to-end encryption.
Smart features needThe server to read messages to find plans, memories and answers.

Two chat modes, chosen per chat and shown clearly. Normal chats get TLS, encryption at rest, strict membership checks and smart features. Private chats use end-to-end encryption (libsignal), and every smart feature is off because the server cannot read them. The mode is visible in the chat header, and switching needs everyone's agreement.

2. Memories about other people

Useful"Mei is vegetarian" helps when planning a dinner.
RiskyA fact said in one chat must not surface in another chat Mei is not part of.

Memories live inside the chat they came from. They are visible only to that chat's current members, disappear when the source message is deleted, and the person a memory is about can see and remove it. Nothing is shared across chats in v1.

3. Web first vs phone first

Built so farA web client and landing page.
RealityPersonal chat happens on phones, with push notifications.

Web for the messaging core, then the phone apps immediately after. The protocol is generated for every client, so the phone apps reuse the same server with no API changes. Anyone testing Lynk with friends needs the phone app before the smart features matter. Whether that is one Expo app or separate iOS and Android apps is still open (see Progress).

4. The spec's workplace features

Spec asks forWorkspaces, five roles, audit logs, capsules, a knowledge graph, a conversation map.
Personal chat needsGroups, a few admin controls, and privacy people can understand.

Cut or shrink them. Group admin and member are the only roles, auditing becomes a personal security log, and capsules, the graph and the map wait until real use shows a need. The engineering ideas behind them (permission-aware retrieval, sourced suggestions) stay.

5. AI cost without business customers

CostEvery smart feature spends tokens or GPU time.
UsersPeople expect personal chat to be free.

Keep the free tier cheap and never show ads. Cheap rules run before any model call, extraction uses Claude Haiku 4.5 through the Batch API, embeddings and transcription are self-hosted, and each user has a monthly budget. A later "Lynk Plus" subscription can raise the limits.

System architecture

One Go binary in three roles: api (HTTP + WebSocket), worker (background jobs) and relay (outbox to NATS). Web and mobile speak the same protocol.

Send path (never waits for AI)

  1. Client creates an idempotency key and shows the message as sending.
  2. Gateway checks membership, blocks and rate limits.
  3. One transaction: message with the next per-chat seq, plus an outbox event.
  4. Ack the sender, then fan out to every member's devices through NATS.
  5. Offline members get a push notification.

After the ack (normal chats only)

  1. Embed the message for search.
  2. Cheap rules look for times, places, questions to someone, and lists.
  3. Only likely candidates go to the model, which suggests a plan, to-do or memory.
  4. Suggestions appear for the chat to save or dismiss.
  5. Voice notes are transcribed and messages translated for members who want it.

WebSocket

Event protocol

One authenticated socket per device. Every event is safe to process twice.

{
  "v": 1,
  "id": "evt_01J9…",      // unique, used to deduplicate
  "type": "MESSAGE_CREATE",
  "ts": "2026-09-24T14:03:11.402Z",
  "chat_id": "ch_…",
  "side_chat_id": null,
  "seq": 4182,            // per-chat order
  "correlation_id": "req_…",
  "payload": { … }
}

Event types

MESSAGE_CREATE · MESSAGE_UPDATE · MESSAGE_DELETE · REACTION_ADD · REACTION_REMOVE · TYPING_START · TYPING_STOP · PRESENCE_UPDATE · READ_UPDATE · CHAT_CREATE · CHAT_UPDATE · MEMBER_UPDATE · SIDECHAT_CREATE · PLAN_SUGGESTED · PLAN_SAVED · PLAN_RSVP · TODO_SUGGESTED · TODO_SAVED · TODO_DONE · LIST_UPDATE · MEMORY_SUGGESTED · MEMORY_SAVED · NOTIFICATION_CREATE · SYNC_REQUIRED

Client to server: HELLO with resume cursors, SEND, TYPING, ACK, PING.

Reconnect and ordering

  • HELLO carries the last seq per open chat. The server replays gaps, or sends SYNC_REQUIRED for large gaps.
  • Clients drop duplicate event IDs and buffer events that arrive ahead of a missing seq.
  • Unsent messages stay in the local outbox and retry under the same idempotency key.

Privacy model

Simpler than roles and capabilities: access comes from being in the chat. Smart features follow exactly the same rule.

Who can see what

  • You can read a chat's messages from your joined_at onward, unless the group admin shares earlier history when adding you.
  • Group admins can rename the group, add or remove people, and change settings. Members can leave at any time.
  • Blocking hides messages, presence and invites in both directions.
  • Plans, to-dos, lists and memories inherit their chat's access. They never appear outside it.

Smart features that cannot leak

  • One SQL function, visible_messages(user_id), defines readable content, including join time, deletions and blocks.
  • Search and answers filter through it inside the query, so the model only sees permitted messages.
  • Private chats are never embedded, indexed or sent to a model.
  • Mandatory leak tests: people who left a group, were blocked, or joined late never retrieve content they should not.

Background jobs

Flow

  1. Writes add an outbox row in the same transaction.
  2. The relay publishes to JetStream subjects such as lynk.msg.created.
  3. Durable consumers: push, embed, spot, transcribe, translate, notify.
  4. Jobs are idempotent, keyed by source ID and prompt version.

When things fail

  • Retries with backoff, then a dead-letter stream and a replay view.
  • A circuit breaker per AI provider pauses smart features during outages.
  • Messaging never depends on AI, Redis or storage being up.
Smart features

Each one solves a real annoyance in group chats, suggests rather than decides, and links back to the messages behind it.

Evaluation

  • A seeded set of synthetic friend and family chats with labelled plans, to-dos, memories and search questions.
  • Metrics: plan and to-do precision and recall, search recall@10, citation correctness, unsupported-claim rate.
  • Runs in CI when prompts, models or retrieval change. Leak tests run on every build.
What could go wrong

Risks

High

Memories about people who never agreed

Keep them scoped to one chat, visible to its members only, removable by the person described, and deleted with their source.

High

Smart features leaking across chats

Access filtering inside the search query, no cross-chat memories, and leak tests covering people who left, were blocked or joined late.

High

Privacy expectations

Say plainly which chats the server can read. Private mode must be real end-to-end encryption, with an external review before launch.

Med

Spam and abuse

Invite-based contact, rate limits on new accounts, blocking, and reporting from day one. Required for the app stores anyway.

Med

AI cost on a free product

Rules before models, Haiku and batching, self-hosted embeddings and transcription, and per-user budgets.

Med

Prompt injection in messages

Messages are treated as untrusted data. The model only suggests; every field is validated before saving, and it can never take actions.

Low

Wrong suggestions

Nothing is saved without a tap, and dismissing is one tap too.
